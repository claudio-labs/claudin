**Scope:** this file owns the BUILD side — compile flags, package assembly,
vendoring, the binary's own path resolution and the update flow. The release and
publish side (why `release-binaries.yml` is the sole path, the OIDC rule, the
privacy gate, publish order and the npm gotchas) is
[[binary-release-rollout-state]].

Phase 2 of the compile initiative (2026-07-14, branch `perf/compile-binary-poc`, off main): claudin distributes native per-platform binaries via npm, mirroring Claude Code's wrapper model. Startup ~409ms vs ~727ms Node.

**Build** (`scripts/build/build.ts`, gated `CLAUDIN_COMPILE=1`): `target:'bun'`, `format:'cjs'`, `bytecode:true`, `splitting:false`, `sourcemap:'none'`, `compile:{target: CLAUDIN_COMPILE_TARGET||host, outfile: dist/bin/<platform>/claudin[.exe]}`. Platform key = target minus `bun-`, `windows`→`win32`. The 4 installed provider SDKs (google-auth-library + @anthropic-ai/{bedrock,vertex,foundry}-sdk) bundle IN when isCompile; AWS/Azure stay external both builds (undeclared BYO, guarded in model/bedrock.ts). Drivers: `build:compile` (host), `build:compile:all` (all 8 / win-arm64 fallback), `vendor:ripgrep`, `build:packages`.

**Distribution** (`assemble-packages.ts` → `dist/packages/`): wrapper `@claudiolabs/claudin` (bin `./bin/claudin.exe` stub + `install.cjs` postinstall + `cli-wrapper.cjs` + Node-fallback `dist/cli.mjs` + `optionalDependencies` pinning 8 platform pkgs) and `@claudiolabs/claudin-<platform>` each with the binary + vendored rg + **`os`/`cpu`/`libc` fields** (CRITICAL — without them npm pulls all 8 × ~212MB). `install.cjs` hardlinks the matching binary over the stub AND mirrors the platform pkg's `vendor/` beside it. `cli-wrapper.cjs` = --ignore-scripts fallback (spawn native, else Node bundle).

**ripgrep gotcha (SOLVED):** in a Bun compiled binary the bundled module's `__dirname` is the in-binary VFS (`/$bunfs/root`), NOT the real FS — so `ripgrep.ts` (`resolveVendoredRipgrepPath`) also probes `dirname(process.execPath)/vendor/ripgrep/<arch>-<platform>/rg`, and **realpathSync-resolves execPath first** (the npm global bin is a symlink into node_modules/.../bin — without realpath, dirname(execPath)=global bin dir=no vendor/ → silent system-rg fallback). Vendor rg there. In the native matrix each leg copies its own `@vscode/ripgrep` rgPath (right platform+libc, incl. musl). Validated: Grep correct with a broken system rg on PATH.

**Update flow = via npm (channel A):** `getCurrentInstallationType()` (`src/platform/doctor/doctorDiagnostic.ts`) now returns `npm-global` for a bundled binary under an npm path (extracted `isNpmGlobalInstallPath`), so `claudin update` runs `npm i -g` (re-hardlink), not the native updater. The Anthropic `GCS_BUCKET_URL` in `src/platform/install/download.ts` is neutralized (empty + throw) — defense-in-depth. NOTE: `isInBundledMode()` (`src/platform/install/bundledMode.ts`, =`Bun.embeddedFiles.length>0`) is actually FALSE for a plain `--compile` (we embed nothing), so the binary never classifies `native` anyway; the fix is robustness if we ever embed files.

**Key facts:** strip (even `--strip-debug`) BREAKS Bun standalone binaries (truncates the appended payload → reverts to Bun runtime) — ship unstripped, ~212MB raw / ~68MB gzipped download.

**sharp NOW VENDORED (2026-07-14, was SKIPPED):** the standalone binary has no node_modules beside it, so the bare `import('sharp')` failed → clipboard-image paste + all image resizing silently no-op'd (`getImageFromClipboard` swallows the throw → null). Fix = `scripts/build/vendor-sharp.ts` (`vendor:sharp`, wired into release-binaries.yml beside vendor:ripgrep) ships a self-contained sharp install at `vendor/sharp/node_modules/` (sharp + detect-libc + semver + @img/colour + `@img/sharp-<key>` + `@img/sharp-libvips-<key>`; key = sharp's runtimePlatformArch, musl→`linuxmusl`; no separate libvips pkg for win32). `install.cjs` already mirrors the WHOLE `vendor/` beside the binary and assemble-packages ships `vendor/` — so it rides along, no changes there. Runtime probe: `imageProcessor.ts::resolveVendoredSharp()` requires sharp's main by ABSOLUTE PATH beside `realpathSync(execPath)`. **Bun-compiled-binary resolver gotchas (verified empirically, 1.3.11):** its external resolver IGNORES package.json `main` AND `exports` — only finds a root `index.js` or a literal subpath file. So vendor-sharp (1) drops `index.js` shims on detect-libc/@img/colour (main→subdir), and (2) rewrites sharp.cjs's `require("@img/sharp-<key>/sharp.node")` (exports-mapped) → `/index.cjs` (real file; its relative `./lib/*.node` require keeps the addon's `$ORIGIN` RPATH so libvips resolves in the sibling libvips pkg). Also: `sharp` still in build.ts `external` for BOTH builds. Complements option-1 hotfix (imageResizer.ts fallback lets small images through when no processor). Rollout = straight to `latest`, all 8 platforms, unsigned (README documents mac xattr / Windows SmartScreen).

**CI (build side):** the native build matrix in `.github/workflows/release-binaries.yml` is 8 runners — ubuntu x64/arm64, macos-13/14, windows-latest/11-arm, alpine containers for musl — one leg per platform package, each vendoring its own rg (and, since 2026-07-14, sharp). Bootstrap publish of the 8 platform pkgs at `0.0.0` DONE 2026-07-14. Everything downstream of the matrix — the version/publish jobs, OIDC, the privacy gate and publish order — is [[binary-release-rollout-state]].
