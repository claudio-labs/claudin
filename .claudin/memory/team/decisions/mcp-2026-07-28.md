**Decision:** Claudin's MCP client and `mcp serve` run on `@modelcontextprotocol/client`/`server`/`core` 2.4.0 and
speak 2026-07-28 where a server offers it (PR #373, squash-merged 2026-11-28 as 0dcac8a9; plan
`.claudin/plans/clever-foraging-engelbart.md`).
- **Order (user's call, second "está elegante?" round):** cover suites → red repro commit → migration with the
  legacy wire byte-identical → fix only what stayed red on v2 → features. No fix was written on 1.x first,
  because the migration would have rewritten it (the serve handler's signature, the provider's `ctx.issuer`).
- **Negotiation:** `auto` on http AND stdio; sse/ws/ide/sdk/claudeai-proxy stay legacy. The probe gets
  `min(5 s, startup)`. Only a 5xx or a timed-out probe reconnects as 2025-11-25 on a fresh transport (Spring AI
  answers 500); a network error fails the attempt, and the transient retry probes again in `auto`.
  - The verdict is cached on disk (`<config home>/mcp-era-cache.json`) and replayed with `connect(t, {prior})`.
    stdio replays both eras (modern: discover `ttlMs` clamped 1–24 h; legacy 24 h), so the sibling probe's
    double spawn happens only on a cache miss. HTTP replays only a LEGACY verdict, which saves the probe a 2025
    server answers 400, and never writes a modern one: adopting a modern prior sends nothing, so a server gone
    back to 2025 stayed "connected" with no tools, and the replayed `DiscoverResult` kept stale capabilities.
  - A reconnect the user asks for (`/mcp reconnect`, headless `mcp_reconnect`) drops the verdict first; the
    automatic retry keeps it.
- **Config:** per server `protocol: 'auto'|'legacy'` (http, stdio) and `extensions: {skills?, tasks?, events?}`
  (on by default; also on sse, ws and claudeai-proxy, where skills run on the 2025 wire).
  The only global switch is `MCP_PROTOCOL_NEGOTIATION=legacy`, Claude Code's name. It turns tasks and events off
  too, since both exist only in 2026-07-28.
- **Wire:** a pre-connect `onmessage` hook plus a `send` wrapper on the transport instance, driven by the rule
  table in `wireRules.ts`. Lists come from the SDK's `listTools()` and friends. The filter:
  - checks list entries one by one;
  - fills `resultType` on every modern result, and `ttlMs`/`cacheScope` on lists, `resources/read` and
    `skills/list` — the SDK rejects a modern result missing one;
  - strips `outputSchema` (Claudin never enforced structuredContent; Portainer violates its own schema);
  - cuts cursor cycles, and stops a listing at 100 pages keeping its entries, as the old pager did (the SDK's
    `listMaxPages` is set to 101, since its own 64-page cap throws the whole list away);
  - rewrites the 2025 `initialize` capabilities to exactly `{roots:{}, elicitation:{}}` (the SDK-control
    clients in `sdkClients.ts` keep the `{}` they are built with);
  - turns a `resultType:'task'` reply into a marker.
- **Auth:** v2 does RFC 9207 `iss`, `application_type` and the per-issuer stamps. Claudin passes `iss` from the
  callback and detects a moved authorization server in the provider. It keeps a static `Authorization` header
  over stored tokens, as 1.x did. `prompt=consent` with `offline_access` is kept, as the SDK and Claude Code do.
- **Features (all four extras taken, then Skills + Events too):**
  - URL elicitation on modern connections only.
  - Completions for MCP prompt arguments only (Claude Code completes resource templates, which was not chosen).
  - Resource-change notice: subscribe on read or @-mention, one tail line, 50 URIs per server. Every connect
    re-subscribes what the conversation read on the server before, so a reconnect keeps them. Claude Code has none.
  - TTL refresh at turn start, REPL and headless alike: 60 s floor, replaced only on a hash change, all of a
    server's changed lists in one write.
  - Tasks (`taskCall.ts`, `taskPoll.ts`): polled inline for `min(120 s, toolTimeout)` (`MCP_TASK_INLINE_MS`),
    then handed to a background `monitor_mcp` task on the main thread. 120 s is a fixed number, the user's — NOT
    the Agent's `getAutoBackgroundMs()`, which is 0 unless `CLAUDIN_AUTO_BACKGROUND_TASKS` is set. Where nothing
    can run in the background (sub-agent, `-p`), the poll ends at the tool timeout with the normal timeout error.
    `tasks/cancel` goes out on stop, at exit (the inline window included), at that timeout and on a failed
    `tasks/get`/`tasks/update`. A task's `roots/list` input gets the connection's roots (`listRootsResult()`);
    any other input method Claudin does not support (sampling…) cancels the task with a tool error naming it, so
    nothing waits out the ttl. A task answer without a `taskId` is a tool error.
  - Events: model-driven through Monitor's `mcp_event: {server, event, args?}` source (one optional schema
    field, ~+220 tokens when Monitor is loaded). ListMcpResources lists the event types, so no new tool.
    - Push streams (any type that lists no `delivery`) keep a heartbeat watchdog (3× `heartbeatMs`) and resume
      from the cursor, also when the server ends the stream (`onRequestStreamEnd`) without `heartbeatMs`.
      Types without push are polled (1 s floor, `truncated` reported as a possible gap). An error
      notification fails the task.
    - Each event is a task-notification under Monitor's 2 KB, flood and timeout caps, and always asks
      permission, like a `ws` monitor. Its first line is the untrusted marker, holding no server text; every
      server string (event name, id, error, transport error) follows it JSON-quoted and cut at 200 chars.
  - Both Tasks and Events live on the existing `monitor_mcp` task type, kinds `call`/`events`.
  - MCP Skills: on by default with a per-server opt-out; a modern client announces the extension in its
    capabilities. SKILL.md is read on invocation (digest and size verified), and ReadMcpResource refuses files
    outside the skill's manifest. Frontmatter `allowed-tools` and `hooks` are dropped, so a remote server can
    neither grant tools nor register hooks that run shell on the user's machine.

**Why:** SDK 1.32.2 is the last 1.x and tops out at 2025-11-25; v1 fixes end ~2027-01. Claude Code 2.1.332 already
negotiates 2026-07-28 by default. The user asked for the newest protocol, extensions included ("vamos estar na
última versão do protocolo?").

**What changes for a teammate:**
- A new MCP wire quirk goes in `wireRules.ts` as a rule, not in an SDK patch.
- The test gotchas (both eras, the era cache, the fetch memos keyed by server name) are in `testing.md`,
  "Process-global state a test file must put back".
- `@modelcontextprotocol/sdk` survives only as a devDependency for legacy-server fixtures, enforced by
  `src/__tests__/mcpSdkV1TestOnly.test.ts`.
- SDK facts this rests on, and the recipe to re-run the live check: [[mcp-sdk-v2-verified-behaviors]].
- What the cover suites pinned and left unfixed: [[mcp-latent-bugs-pinned-2026-11-27]].

**Rejected:**
- stdio legacy by default (chosen first, reversed once the era cache made the double spawn a once-per-TTL cost).
- Replaying a cached modern verdict over HTTP (review round, 11-28): it saved one `server/discover` per connect
  and hid both a downgrade and new capabilities.
- A `bun patch` of the SDK as opencode did: re-applied on every bump, and opencode patched tools only.
- A separate `mcp_task` type: it would have needed new arms in two React Compiler `.tsx` files that `monitor_mcp`
  already has.
- `CLAUDIN_MCP_TASKS`: redundant with `MCP_PROTOCOL_NEGOTIATION=legacy`.
- The Events webhook: a CLI has no https endpoint.
- sampling, logging/setLevel and roots `listChanged`: deprecated or removed in 2026-07-28.
- Tying the task inline window to `getAutoBackgroundMs()`. It is opt-in and 0 by default, so out of the box
  the window became the 5-minute tool timeout. The planning question had wrongly described that 120 s timer
  as always on, and the user's answer named the number.
- Enforcing outputSchema. Stripping `prompt=consent`.
