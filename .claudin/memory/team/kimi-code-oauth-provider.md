Kimi Code (Moonshot subscription) was added to `/provider` as an **OAuth device-flow (RFC 8628)** provider on branch `feat/kimi-code-oauth-provider` (implemented 2026-07-18, uncommitted / not yet PR'd as of that date). It is a near-clone of the existing **xAI/Grok OAuth** provider: rides `provider:'openai'` / `transport:'openai_compat'`, detected purely by baseURL host `api.kimi.com` via `isKimiCodeBaseUrl` (baseUrl `https://api.kimi.com/coding/v1`, default model `k3`, `requiresApiKey:false`). Tokens live in secure storage under a new `kimiCode` key; a non-secret `kimiDeviceId` is a sibling key.

**Reverse-engineered wire format is documented in `docs/tech/kimi-code/wire-format.md`** — device_authorization/token endpoints on `auth.kimi.com`, the public `client_id`, grant types, and the required `X-Msh-*` device headers + `User-Agent: kimi-code-cli/<ver>`. This doc is the source of truth for the endpoints/headers (like the windsurf/devin RE docs).

**Deliberate gray-area decision:** the provider **impersonates the official Kimi CLI** by sending `User-Agent: kimi-code-cli/0.27.0` + `X-Msh-Platform: kimi_code_cli` + device headers on every outbound request. This is intentional and documented in the wire-format doc (a ToS gray area, not a defect).

**Why:** users with a Kimi Code subscription can sign in via browser device-flow instead of pasting an API key.

**K3 thinking-effort levels (2026-07-18 capture):** `k3` is the only Kimi model with granular effort. The official CLI sends `thinking: { type: 'enabled', effort: <low|high|max>, keep: 'all' }`; it does **not** use OpenAI's `reasoning_effort`. Other Kimi models (`kimi-for-coding`, `kimi-for-coding-highspeed`) only support `thinking` on/off. Claudin's `/effort` for K3 therefore maps to the Kimi levels `[low, high, max]` and serializes them as `thinking.effort`.

**How to apply:** when touching this provider, mirror xAI's structure (kimiOAuth/kimiCredentials/kimiDeviceHeaders/useKimiOAuthFlow). The xai+kimi per-request auth wiring (token swap + UA + `X-Msh-*` headers) was extracted (2026-07-18) into a **data registry `OAUTH_WEB_PROVIDERS`** in `openaiShim/oauthProviderAuth.ts`, consumed by both `messagesClient` (`resolveOAuthProviderAuth`) and `withRetry`'s 401 force-refresh (`forceRefreshOAuthWebTokenOn401`) — adding a 3rd OAuth-web provider is one array entry, not new `if`s in two files. Codex stays OUT of the registry (transport-keyed, no UA/headers). The per-request keychain-read perf follow-up is now **RESOLVED**: a 30s in-process credential cache in `kimiCredentials.ts`, invalidated on save/clear. Three review rounds (2026-07-18) found no correctness bug and confirmed security clean (exact-host pinning, no token in logs, only the public device-flow `client_id` versioned).

**Post-review cleanup (2026-07-18, all RESOLVED):**
- **Dead `kimi-code` preset removed** — deleted the `providerProfiles.ts` case + `ProviderPreset` union member + its test. The OAuth path already builds its profile inline (`KIMI_OAUTH_*` consts in ProviderManager); the API-key menu routes to `moonshotai`. No preset indirection remains.
- **`isKimiCodeBaseUrl` tightened to require the `/coding` path** (was host-only), now co-extensive with `isMoonshotCompatibleBaseUrl`. A bare `api.kimi.com` or non-coding path no longer triggers token-swap/device-headers. Callers only pass the real `/coding/v1` baseUrl (via the registry), so behavior is unchanged for shipped configs.
- **Test gaps closed**: `resolveOAuthProviderAuth`'s refresh-throws `.catch` fallback (fetch-throw → stored-token reuse), the JWT-exp fallback in `kimiCredentials` (future-exp + opaque-token cases), and exact-content assertions on `X-Msh-*` device headers. Remaining low/untestable-cheaply: natural 30s-TTL cache expiry (needs an injectable clock).

**OAuth re-login now UPSERTS (2026-07-18):** the Kimi `onConfigured` (`ProviderManager.tsx`) used `addProviderProfile` (always append) → a re-login spawned a duplicate "Moonshot AI" profile AND a profile created with an older single-model `KIMI_OAUTH_PROVIDER_MODEL` (e.g. `model:'k3'`) stayed stale, so `/model` (`getModelOptions`→`getProfileModelOptions`→`parseModelList(profile.model)`) only listed `k3`. Fixed by mirroring Codex's upsert: new `findKimiOAuthProfile(profiles, readKimiCredentials()?.profileId)` (falls back to baseUrl==coding-host + no apiKey) → `updateProviderProfile` on match (refreshes model list + clears the profile's stale `openaiAdditionalModelOptionsCache`), else append; then `setActiveProviderProfile` explicitly. Note: `/model` reflects `profile.model` faithfully; the official Kimi CLI's 3 models (K2.7 Coding / Highspeed / K3) come from its own catalog, not ours.

**Stale Kimi model list self-heals on startup (2026-07-18):** a profile created by an early build carried only `model:'k3'`, so `/model` hid the coding models (re-login upsert fixes it but requires re-login). Added `healStaleKimiCodeModelList()` to `claudinStartupMigrations.ts` (runs via `preActionHook.ts` on every launch): upgrades a Kimi OAuth profile (coding host + no apiKey) whose models are a strict subset of the canonical set to `KIMI_CODE_MODEL_LIST` (new shared const in `kimiOAuthShared.ts`, referenced by ProviderManager's `KIMI_OAUTH_PROVIDER_MODEL` too) and clears its stale `openaiAdditionalModelOptionsCache`. Idempotent; leaves static-key or custom-model profiles untouched. So existing stale profiles fix themselves on the next `claudindev` restart — no re-login needed.

**Append-on-relogin was a class bug across OAuth `onConfigured` flows — all upsert now (2026-07-18):** applied the same fix to **xAI** (`findXaiOAuthProfile` by `readXaiCredentials()?.profileId`, fallback baseUrl==`DEFAULT_XAI_BASE_URL`+no apiKey) and **Anthropic** (`findAnthropicOAuthProfile` by signature only — Anthropic OAuth stores tokens in the credentials file with no per-profile id, so match `provider=='anthropic' && baseUrl==defaults.baseUrl && !apiKey`). Codex already upserted (`findCodexOAuthProfile`). GitHub Copilot device flow persists inside `GithubDeviceFlowStep` (no `addProviderProfile` in ProviderManager), so it's out of this family. All four helpers live together near `findCodexOAuthProfile` in `ProviderManager.tsx`.
