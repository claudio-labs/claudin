Two findings from a 2026-07-13 startup-perf pass (claudindev vs claude; "Claudin is slower").

**FIXED — v8cache GC blocked exit.** `bin/claudin` fired the compile-cache sweep in-process via `import('scripts/v8cache-gc.mjs').then(m => m.gcV8Cache(...))`. The pending promise + its ~10k sequential `stat()`s (cache was 9.8k files / 209MB) kept the event loop alive, so the process couldn't exit until the sweep finished — **~334ms added to every launch**. Invisible in a long REPL (runs concurrently with a longer init) but dominated fast-path exits: `--version` was 361ms (vs claude 67ms), `--help` 335ms. The raw Claudin bundle boots in ~23ms — faster than claude — so this was the whole gap on scripted paths.
- **Why:** async fs ops ref the libuv loop; nothing unref'd it. `CLAUDIN_V8CACHE_GC=0` dropped `--version` to 27ms, proving it.
- **How fixed:** `bin/claudin` now spawns `node scripts/v8cache-gc.mjs <dir> <ttlDays>` **detached + unref'd** (never delays exit), throttled to once/day via a `.gc-stamp` mtime check. `v8cache-gc.mjs` got a `import.meta.main` CLI guard (tests import `gcV8Cache` directly, unaffected). Result: `--version`/`--help` → 27ms. Env overrides unchanged (`CLAUDIN_V8CACHE_GC=0`, `CLAUDIN_V8CACHE_TTL_DAYS`). Not bundled — no rebuild needed for these two files.

**CAVEAT — `CLAUDE_CODE_PROFILE_STARTUP=1` checkpoint deltas over-attribute across `await`.** The timeline showed `setup_after_release_notes` = ~135ms and I first blamed `getRecentActivity()` parsing 10 huge transcripts. WRONG: raw head+tail I/O for those 10 files is ~5ms warm; gating the whole block off (`CLAUDIN_RN_SKIP`) saved only **24ms** end-to-end. The other ~110ms is concurrent background work (`void`-fired tasks) draining during that await — it just moves to the next await when the block is removed. **Lesson:** for any checkpoint that brackets an `await`, the delta ≈ that call's work PLUS whatever background work drains; verify a suspected offender by actually removing it and diffing `repl_first_paint`, not by reading the delta. Did NOT "fix" release-notes — 24ms isn't worth degrading the feature.

**Still open:** interactive REPL first-paint (~720ms warm vs claude ~350ms) is NOT helped by the GC fix — it's dominated by app module-eval (`main_tsx_entry` ~228ms + `profiler_initialized` ~133ms of JS parse/eval), which is inherent to bundle size. Would need a CPU profile of the chunk-eval/mount path to attack.

**TRIED & REVERTED — safe async deferrals don't move interactive first-paint (2026-07-13).** CPU profile of the no-args launch (`node --cpu-prof dist/cli.mjs`, /exit) showed ~345ms module eval + ~90ms subprocess. But the subprocess work is already async/parallel/memoized (`getSystemContext`/`getGitStatus` context.ts, `gitExe`/`getIsGit` memoized). Attempted two deferrals: (1) early-kick the CLAUDE.md external-includes scan (interactiveHelpers.tsx:194) to overlap MCP-approval I/O; (2) drop the `await` on `getRecentActivity()` (setup.ts:382). **Clean back-to-back N=18 A/B: baseline 723ms vs change 730ms — identical (min 711 vs 713).** Both no-ops for first paint: the `release_notes` checkpoint "improved" 144→66ms but total didn't budge (drain redistribution again), and `getRecentActivity` must finish before the logo (stable subtree, Messages.tsx:55) renders anyway, so it's on the critical path regardless of await. **Don't re-attempt async-deferral micro-opts here — the pre-paint cost is CPU-bound (module eval + React/Ink mount), not awaited I/O.** Also ruled out: disabling compile cache (+146ms regression), skipping heap-bump re-exec (execve is in-place, no gain), build-time cache warming (cold-populate vs warm-reuse ~9ms). Only real lever left = shrink/lazy-load the `main.tsx` import graph (big refactor, not attempted).

**TRIED & REJECTED — the "big refactor" has almost no surface, and GC-flag tuning is a no-op (2026-07-14).** Warm CPU profile (through the launcher, compile-cache on) source-mapped the ~770ms pre-paint: **CJS↔ESM interop tax ~195ms** (`v99wm22s` = Bun runtime helpers `__toESM`/`__esm`, imported by 427 chunks — scales with # eager chunks, not a hotspot) + **React/yoga first render ~115ms** (inherent) + **parse ~116ms warm** (compile-cache-bound) + **5.4MB mega-chunk eval ~75ms** + **zod ~60ms** (base lib ~39ms not deferrable). ~100 of 1359 chunks execute pre-paint. Crucially: **`main.tsx` is ALREADY aggressively lazy** (`getLaunchRepl`/`getGetTools`/`getInitBootstrap`/coordinator/assistant/plugins + provider shims `createOpenAIShimClient` client.ts:202 all behind `require()`/`await import()`), so there's little left to defer. Deferring `getTools` (main.tsx:410) can't unload the mega-chunk because `marked` is eager via `claudemd.ts:32` (`Lexer`, runs in `getUserContext`) and `yaml` via settings parsing — and `tools` threads through `setup()`→`launchRepl` (system prompt/perms/autocomplete). Also tested `--max-semi-space-size=64/128` via NODE_OPTIONS (launcher re-execs with node flags anyway) to cut the ~63ms startup GC: **772→775/777ms, no change** (startup minor-GC churn isn't reduced by a bigger young-gen). **Practical floor ≈ 500–600ms; ~720–770ms is close to it.** Further gains need a DIFFERENT, larger project (dep-slimming: replace `marked`/`yaml`/trim `zod`; or progressive first-render Ink rewrite; or a V8 build-snapshot — all high-effort/uncertain). User decided 2026-07-14 to STOP and ship only the GC fix.

**ROOT CAUSE of the claude-vs-claudin startup gap: PACKAGING, not bundle size (2026-07-14).** Inspected the installed `@anthropic-ai/claude-code@2.1.207`: `bin/claude.exe` is a **248MB native ELF compiled with `bun build --compile`** (Bun 1.4.0, JavaScriptCore engine) — confirmed by the `$bunfs`/`/$bunfs/root/` standalone VFS marker + JSC strings + per-platform `optionalDependencies` (darwin/linux/win × arm64/x64 × musl). It embeds the whole app as ONE module in `$bunfs` (not 100 code-split chunks), plus native addons (`audio-capture.node`) and HEAVY deps (mermaid). **So Claude's bundle is BIGGER, not smaller — my earlier "smaller bundle / less init" note above is WRONG.** Claude starts in ~350ms because a compiled Bun/JSC binary skips Node's per-launch tax entirely: no filesystem module resolution, no CJS↔ESM `__toESM` interop across chunks (~195ms in claudin), no compile-cache populate/GC, no heap-bump re-exec, and JSC cold-start < V8. claudin's `scripts/build.ts` already uses `Bun.build({ target: 'node' })` → emits `dist/cli.mjs` + 174MB of chunks run by Node. **The real optimization lever = switch claudin to `bun build --compile` (single native binary), distributed per-platform like Claude.** This attacks the interop + parse + resolution + re-exec costs together — the only thing that plausibly moves ~770ms toward ~350ms. Work/risks: per-platform CI builds, ~250MB artifacts, native-addon handling, dynamic `require()`/`import()` under compile, interaction with the `feature()` preprocessing pipeline, and the `bin/claudin` launcher (heap-bump + compile-cache logic) becomes moot. Not yet attempted; local bun is 1.3.11 (supports `--compile`).

**POC DONE — Bun `--compile` cuts interactive first-paint 727→409ms (2026-07-14, branch `perf/compile-binary-poc`, commit 2e23b61).** Added opt-in compile path to `scripts/build.ts` gated on `CLAUDIN_COMPILE=1` (`bun run build:compile`): same object passed to `Bun.build`, but `target:'bun'`, `format:'cjs'` (bytecode needs CJS), `splitting:false`, plus `compile:{ target:'bun-<os>-<arch>', outfile:'dist/claudin', autoloadDotenv:false, autoloadBunfig:false }` and `bytecode:true`. **All existing plugins (noTelemetryPlugin, bun-bundle-shim, native/text stubs) + define + feature() preprocessing work unchanged under compile.** Post-build help-capture/chunks-GC guarded to non-compile; success branch reports the binary. Compiled clean first try → 238MB bun-linux-x64 binary. `--version`/`--help`/interactive-launch all work, logo renders, and `CLAUDE_CODE_PROFILE_STARTUP` profiler works under Bun/JSC. **N=15 median A/B: compiled `./dist/claudin` 409ms (min 400) vs `node`/claudindev 727ms (min 718) = 318ms / 44% faster** — matches Claude's ~350-413ms. Mechanism confirmed in the profiler: pre-profiler module load 133→71ms, `main_tsx_entry` 228→145ms (parse+interop vanished). Dual-track preserved: default `bun run build` still emits `dist/cli.mjs` for dev/tests/smoke. **Bun standalone binaries CANNOT be stripped (2026-07-14):** `strip` and even `strip --strip-debug` truncate Bun's appended app-payload trailer → the binary silently reverts to a plain Bun runtime (`./bin --version` prints Bun's `1.3.11` instead of the app version). This is why Claude ships its 248MB binary unstripped. Don't add a strip step to the compile pipeline. Size context: a compiled claudin is ~212MB raw but **gzips to ~68MB** = the real `npm i` download (npm ships gzipped tarballs); per-platform optionalDependencies install only the user's platform. Also: dropping the sourcemap for the compile build (`sourcemap:'none'` when isCompile in build.ts) cut ~40MB of dead `.map` beside the binary; the 4 bundled provider SDKs (google-auth-library + @anthropic-ai/{bedrock,vertex,foundry}-sdk) add only ~4MB. AWS/Azure SDKs stay external in BOTH builds (undeclared BYO deps, dynamically imported + try/caught in model/bedrock.ts).

**Feature parity VALIDATED under the binary (2026-07-14, Anthropic-OAuth env, Linux x64):** headless `-p` all exit 0 — provider round-trip (`claudeAiOauth` cred read + `@anthropic-ai/sdk` streaming, bundled) returned the expected token; Grep tool worked (ripgrep spawns via the **system `rg` 15.1.0 fallback** since `@vscode/ripgrep` isn't beside the binary — `src/shared/fs/ripgrep.ts:82-100`); Bash tool exec'd (`child_process` under Bun) with `--allowedTools`; Read tool read `package.json`. Interactive launch paints logo+REPL. So the **core agent loop has full parity on the default Anthropic path**. Untested here: MCP (none configured) and every provider/feature behind the un-bundled `external` deps. **Not yet validated (Phase 2):** the build's `external` array (`build.ts` — sharp, cloud SDKs `@aws-sdk`/`@azure`, `@vscode/ripgrep`, provider SDKs bedrock/vertex/foundry, OTel) is NOT bundled into the binary, so provider calls / image / ripgrep-search / MCP under the compiled binary are untested — startup doesn't touch them (all lazy) so first-paint is unaffected, but Phase 2 must bundle-in (or vendor beside the binary) for feature parity, then do the 8-platform cross-compile + per-platform npm `optionalDependencies` distribution (mirroring Claude).
