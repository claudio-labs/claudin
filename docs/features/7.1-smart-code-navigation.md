# Feature 7.1 — Smart Code Navigation (folded file views)

**Status:** Proposed / design. Not yet implemented.

Claudio gives the model a way to read large code files as a **structural skeleton** — function and class signatures only — and then expand a single symbol on demand, instead of being forced to read the whole file or guess `offset`/`limit` blindly.

## Why it matters

Today, when `Read` hits a file above its size caps (256 KB / 2000 lines / ~25k estimated tokens) there are only two outcomes, and the codebase has measured both:

| Current outcome | Cost | Problem |
|---|---|---|
| **Throw** `"file too large, use offset/limit"` | ~100 bytes | Model is left blind — it picks `offset`/`limit` with no idea where anything is |
| **Truncate at the cap** | ~25k tokens | Expensive, and the cut lands at an arbitrary line |

This is not speculation. `src/tools/FileReadTool/limits.ts:9-13` documents an upstream experiment (#21841, Mar 2026) that tried truncating instead of throwing and **reverted it**: tool-error rate dropped but mean tokens rose, because the throw path yields a ~100-byte error while truncation yields ~25k tokens of content.

A folded outline is the third option that was missing — it is **both** cheap **and** informative. It strictly beats both current outcomes on the over-cap path.

## What it does

Three views over one symbol-scan primitive:

| View | Question it answers | Typical cost |
|---|---|---|
| **outline** | "What's in this file?" | ~1–2k tokens |
| **unfold** | "Show me this one function" | ~0.4–2k tokens |
| **search** | "Where is symbol X across the repo?" | ~3–8k tokens end-to-end |

Compared to ~12k–26k tokens to read a large file in full. (Reference: `src/services/api/openaiShim.ts` is ~2.3k LoC ≈ 26k tokens; an outline of it fits in ~1.5k.)

## End-to-end flow

Real scenario — the model needs one function from `openaiShim.ts`:

```
1. Read('openaiShim.ts')               → exceeds the ~25k-token cap
   ↳ instead of throwing, returns the OUTLINE   (~1.5k tokens, ~80 signatures)
        12-48    export function translateAnthropicToOpenAI(msg, opts)
        93-140   export function translateToolCall(call)
        ...
2. Read('openaiShim.ts', symbol='translateToolCall')
   ↳ exact body of that symbol           (~600 tokens, real line numbers)
3. Grep('retry', output_mode='symbols')  (cross-file)
   ↳ matched signatures across N files
```

End-to-end: **~2k tokens** vs ~26k for the full read.

## Design

One primitive, three views, **no new tool** and **no new dependency**.

### The primitive

```
src/tools/shared/codeOutline/scanSymbols.ts
   scanSymbols(source, lang) → SymbolEntry[]
   SymbolEntry = { name, kind, signature, startLine, endLine, depth, docLine? }
```

A depth-scanner with string/comment masking finds each symbol's end — brace depth for C-like languages, indentation for Python. The end of a symbol is "the next sibling at the same depth or shallower"; no AST is required. Both `outline` and `unfold` slice the **same** table, so their boundaries are always consistent.

v1 languages: TS/TSX, JS/JSX, Python, Go — 100% of the Claudio repo. Rust/Java/C as fast-follow.

### The three views, grafted onto existing tools

| View | Lives in | How |
|---|---|---|
| outline | `FileReadTool` — new `view: 'outline'` param | renders the symbol table |
| unfold | `FileReadTool` — new `symbol: 'name'` param | `slice(entry.start, entry.end)` with real line numbers |
| search | `GrepTool` — new `output_mode: 'symbols'` | rg finds files → `scanSymbols` each → matched symbols |

The capability is grafted into `Read`/`Grep` rather than shipped as a separate tool, for two reasons:

1. **The model already reaches for `Read` by instinct** and hits the wall. If the capability lived in a separate tool, the model would need to *know* to switch tools. Inside `Read`, the wall becomes a map automatically — the over-cap throw is replaced by the outline.
2. **Schema cost.** Two optional params (~190 tokens) vs a whole new always-on tool (~400+ tokens). `scripts/measure-tool-schemas.test.ts` enforces this budget.

### Parser decision

No dependency in v1. The depth-scanner (~80 robust LoC) covers ~95% of cases; anything it cannot scan **degrades to a normal `Read`** (rule 4 of `.claudio/rules/typescript-patterns.md` — fail open, never block the user). `web-tree-sitter` (WASM) stays as a v2 upgrade, taken **only if** telemetry shows the scanner mis-bounding symbols. This de-risks: value now, dependency later only if proven necessary.

## Rollout

Behind `feature('SMART_CODE_NAV')` in `scripts/build.ts`, recommended default **on** (the outline is provably better than both current over-cap outcomes; the flag acts as a kill switch).

- **Phase 1 — keystone:** `scanSymbols` + `FileReadTool` `view`/`symbol` params + auto-outline on the over-cap path. Delivers ~90% of the value: it kills the dead-end error.
- **Phase 2:** `GrepTool` `output_mode: 'symbols'`.

## Architecture (brief)

Touch points once implemented:

1. `src/tools/shared/codeOutline/scanSymbols.ts` — new symbol-scan primitive
2. `src/tools/FileReadTool/` — new `view` / `symbol` input-schema params; over-cap path returns outline instead of throwing
3. `src/tools/FileReadTool/limits.ts` — the over-cap branch documented at lines 9-13 changes behaviour
4. `src/tools/GrepTool/` — new `output_mode: 'symbols'` (Phase 2)
5. `scripts/build.ts` — `SMART_CODE_NAV` feature flag
