# Spec: `sessions/lifecycle`

The eight modules of this unit are `src/sessions/sessionRestore.ts`,
`sessionStart.ts`, `sessionEnvironment.ts`, `sessionState.ts`,
`sessionActivity.ts`, `sessionTitle.ts`, `concurrentSessions.ts` and
`sessionEnvVars.ts`.

## Purpose

What a session does around its conversation, from start to exit:

- **Start.** The SessionStart and Setup hooks run, after the plugin hooks
  are loaded. Their output becomes messages, one additional-context
  attachment, an optional first user message, files to watch, and `export`
  lines for the shell.
- **Restore.** `--continue`, `--resume` and `/resume` rebuild a session from its
  transcript. They take over the session id and its transcript file, restore
  the cost, the metadata, the agent and its model, the todo list and file
  history, and go back to the worktree the session was in. A fork takes the
  conversation and none of that ownership.
- **Environment.** Hooks leave `export` lines in a per-session directory. The
  shell provider sources them, after an optional parent-provided file, before
  every command.
- **Signals.** The session reports idle, running or blocked-on-the-user to
  the remote bridge, the SDK stream and the permission-mode listener. A
  reference-counted heartbeat keeps a remote container alive while work is in
  flight.
- **Title.** A short title is generated by the small fast model.
- **Presence on the machine.** Each running CLI keeps a record under
  `<config dir>/sessions/`. Other instances count those records, list them,
  and read them to reach this session.

## Observable behaviour

### 1. Resuming a session: `processResumedConversation`

**When not forking, with a session id** (`opts.sessionIdOverride`, else
`result.sessionId`):
- **The session is switched** to that id. Its project directory is
  `dirname(opts.transcriptPath)` when a path is given, and unset otherwise, so
  the transcript is looked for in the current project. A transcript from
  another project therefore keeps receiving the session's writes.
- **The transcript pointer is dropped**, so nothing buffered for the previous
  session leaks into the resumed one.
- **The running cost is restored for that id**, with the precedence
  `restoreCostStateForResume` (`src/agent/cost-tracker.ts`) defines: the
  transcript's `cost-state` entry, then the project-config slot, then a replay
  of the loaded messages. `src/sessions/sessionRestore.costState.test.ts` pins
  that precedence.

**In both cases, the metadata is cached for the session:** title, tag, agent
name, color and setting, mode, worktree and PR link. The rules are those of
`restoreSessionMetadata`, and one of them is observable here: a title already
cached (the `--name` flag) is kept over the transcript's. A fork leaves the
worktree out, so a fork never owns the original session's worktree.

**When not forking:**
- **The session returns to its worktree** (section 3).
- **The transcript file is adopted.** The resumed session's transcript
  becomes the open transcript. The cached metadata is re-appended at its end
  at once: `custom-title`, `tag`, `agent-name`, `agent-color`,
  `agent-setting`, `mode`, `worktree-state` and `pr-link`, whichever are set.
  The title is not re-read from the file first, so a `--name` title is the one
  written. Later messages go to the same file.
- **Without a transcript path**, the adopted file is
  `<config>/projects/<current project>/<id>.jsonl`.

**Then, in both cases:**
- **The agent** is restored with `restoreAgentFromSession(result.agentSetting,
  context.mainThreadAgentDefinition, context.agentDefinitions)` (section 2).
- **The process record is renamed** after the session's agent name, when
  there is one (`updateSessionName`, section 8). This is not awaited.

**The result:**
- `messages` is `result.messages`, the same array. `fileHistorySnapshots` is
  `result.fileHistorySnapshots`, and `agentName` is `result.agentName`.
- `agentColor` is `result.agentColor`, except that `'default'` becomes
  undefined.
- `restoredAgentDef` is the restored agent definition, if any.
- `initialState` is `context.initialState` with these changes:
  - `agent`, set to the restored agent type when an agent was restored;
  - `standaloneAgentContext`, set to `computeStandaloneAgentContext(agentName,
    agentColor)` when that is defined;
  - `agentDefinitions`, which is always set: to `context.agentDefinitions`
    itself, unless coordinator mode reloaded them (below).
- **`includeAttribution` has no effect.** No attribution state is ever
  restored, so `initialState.attribution` stays what `context.initialState`
  held.

**Coordinator mode.** This part exists only in builds with the
`COORDINATOR_MODE` feature, which production has. The suite cannot reach it,
because `feature()` is false under `bun test`.
- **The session's mode** is handed to `context.modeApi.matchSessionMode`
  before anything else. When that returns a warning, a system message with
  that text at level `warning` is appended to `result.messages`, the same
  array the result returns.
- **After the agent is restored**, the current mode is cached for the session:
  `'coordinator'` when `context.modeApi.isCoordinatorMode()` is true,
  `'normal'` otherwise, and also when `modeApi` is null.
- **When the mode was switched** (a warning was returned), the agent
  definitions are reloaded for `context.currentCwd`, bypassing the loader's
  memo. `context.cliAgents` are appended to `allAgents`, and `activeAgents`
  is recomputed from that list with `getActiveAgentsFromList`. The result is
  `initialState.agentDefinitions`.

**`renameRecordingForSession`** is still called after the switch, and does
nothing in this build.

### 2. The agent of a resumed session

**`restoreAgentFromSession(agentSetting, currentAgentDefinition, definitions)`:**
- **An agent chosen on the command line wins.** When
  `currentAgentDefinition` is given, it returns `{ agentDefinition:
  currentAgentDefinition, agentType: undefined }` and changes nothing else.
- **A session without an agent** (a missing or empty `agentSetting`) clears the
  main-thread agent type in bootstrap state and returns both fields
  undefined.
- **An agent that is no longer active** is also cleared, with both fields
  undefined and a debug log. The lookup matches `agentType` among
  `definitions.activeAgents` only, so an agent that is defined but shadowed
  does not come back.
- **An active agent** becomes the main-thread agent type.
  - Its `model` becomes the main-loop model override, resolved with
    `parseUserSpecifiedModel`.
  - That happens only when no override is set already, and when the model is
    set and not `'inherit'`.
  - It returns `{ agentDefinition, agentType }`.

**`computeStandaloneAgentContext(name, color)`:**
- It is undefined when both are empty or undefined.
- Otherwise it is `{ name: name ?? '', color }`, where `'default'` becomes an
  undefined color. For example, `('', 'default')` gives `{ name: '', color:
  undefined }`.

### 3. The worktree of a resumed session

**`restoreWorktreeForResume(worktreeSession)`:**
- **A worktree this run already created** (`--worktree`) takes precedence.
  - The worktree already current (`getCurrentWorktreeSession()`) is recorded
    for the session again with `saveWorktreeState`. This matters because the
    metadata restore just overwrote it with the transcript's.
  - The argument is ignored, and nothing moves.
- **`null` or undefined** does nothing.
- **When the directory no longer exists**, it is recorded as exited: the
  session's worktree state becomes `null`, and a `worktree-state` entry is
  appended when a transcript is open. Nothing moves, and no cache is dropped.
- **Otherwise the session enters the worktree:**
  - the process changes into it;
  - `setCwd` and `setOriginalCwd` point at its real path;
  - `getCurrentWorktreeSession()` returns the given object;
  - the project root is left alone, so skills and history stay anchored to the
    original project.

  Everything cached for the old directory is then dropped (the list below).

**`exitRestoredWorktree()`:**
- **Outside a worktree** it does nothing.
- **Otherwise:**
  - the current worktree session is cleared, and every cache below is dropped;
  - the process changes back to the worktree session's `originalCwd`, and the
    cwd and original cwd follow;
  - when that directory is gone, the process stays where it is, and the cwd
    state is left unchanged.
- **The recorded state is not touched.** The session's worktree state is not
  marked as exited here; the callers clear or replace the metadata next.

**The caches keyed to the directory**, dropped on entering and on exiting:
- the instruction files (`getMemoryFiles`), so the new directory's
  `AGENTS.md` is read;
- the system prompt sections, together with the beta-header latches;
- the plans directory memo, so plans go under the new directory's
  `.claudin/plans`;
- the read-only tool-result cache (Read, Glob, Grep, LSP). Its keys carry
  relative paths, so after a directory change it would answer for the wrong
  files.

### 4. State rebuilt from the transcript: `restoreSessionStateFromLog`

- **File history.** When `fileHistorySnapshots` is non-empty and file history
  is enabled (`fileHistoryEnabled()`), the state becomes:
  - `snapshots`: the snapshots, with each tracked path shortened relative to
    the original cwd;
  - `trackedFiles`: the set of those paths;
  - `snapshotSequence`: the number of snapshots.

  In a non-interactive session this needs `CLAUDIN_ENABLE_SDK_FILE_CHECKPOINTING`.
- **Todos.** They are restored only while the v2 task list is off
  (`isTodoV2Enabled()` false: a non-interactive session without
  `CLAUDIN_ENABLE_TASKS`), and only when there are messages.
  - The source is the last assistant message that holds a `TodoWrite`
    tool_use. Its `input.todos` is validated with `TodoListSchema`.
  - A valid, non-empty list is stored under the current session id.
    `todos` entries for other ids are kept.
  - A missing, invalid or empty list restores nothing. That holds even when an
    earlier `TodoWrite` was valid.
- **`setAppState`** is called once per piece restored, and never when there is
  nothing to restore.

### 5. Session start: `processSessionStartHooks` and `processSetupHooks`

**Bare mode.** `isBareMode()` (`CLAUDIN_SIMPLE`, or `--bare` on the command
line) makes both return `[]` at once. No hook runs, and the plugin hooks are
not even loaded.

**Plugin hooks** are loaded (`loadPluginHooks()`) before any hook runs:
- **For SessionStart**, the load is timed in the diagnostics log as
  `load_plugin_hooks_started`, then `load_plugin_hooks_completed` or
  `load_plugin_hooks_failed`.
- **They are skipped** when only managed hooks may run
  (`shouldAllowManagedHooksOnly()`): a policy `allowManagedHooksOnly`, or
  `disableAllHooks` in a non-managed settings file.
- **A failed load never fails the start.** The configured hooks still run.
  - For SessionStart, the error goes to `logError`, and a debug warning adds
    guidance for network, permission and configuration errors.
  - For Setup, only a debug warning is written.

**The hooks** run through the hook engine with the matcher query set to the
`source`, or to the `trigger` for Setup. So a SessionStart hook with matcher
`resume` runs only for `resume`. A SessionStart hook's input carries:
- `session_id`: `options.sessionId`, else the current session id;
- `agent_type`: `options.agentType`, else the main-thread agent type from
  bootstrap state;
- `model`: `options.model`;
- `source`.

**`forceSyncExecution`** is passed through, so an `async` hook contributes its
output only when it is set.

**The result** is every message the engine yields, in order: one
`hook_progress` progress message per matching hook, then the hooks' result
attachments (`hook_success`, errors, system messages). It is followed, when
any hook returned `additionalContext`, by exactly one attachment:
- `type: 'hook_additional_context'`;
- `content`: every context string. With several hooks, the order is the
  order they finished in;
- `hookName`, `toolUseID` and `hookEvent`: all three equal to `'SessionStart'`,
  or to `'Setup'`.

**The other SessionStart outputs:**
- **`initialUserMessage`** is kept until `takeInitialUserMessage()` hands it
  out, once. A later start without one does not clear it.
- **`watchPaths`** of every hook are handed together to the file-changed
  watcher (`updateWatchPaths`), so a FileChanged hook fires when one of them
  changes.
- **`export` lines** a hook writes to its `CLAUDIN_ENV_FILE` land in the
  session environment directory (section 6).

### 6. The session environment

- **The directory** is `<config dir>/session-env/<current session id>`. It is
  resolved at each call, and created when it is needed.
- **`getHookEnvFilePath(event, index)`** is
  `<dir>/<event, lowercased>-hook-<index>.sh`: `setup-hook-0.sh`,
  `sessionstart-hook-3.sh`, `cwdchanged-hook-1.sh`, `filechanged-hook-12.sh`.
  It creates the directory, not the file.
- **`getSessionEnvironmentScript()`** is the text the shell provider runs
  before every command, or `null` when there is nothing to run.
  - **First comes the file named by `CLAUDIN_ENV_FILE`**, trimmed, when it is
    set and holds text. A parent process uses it to keep a virtualenv or
    conda activation across commands.
  - **Then every file in the directory named exactly
    `(setup|sessionstart|cwdchanged|filechanged)-hook-<digits>.sh`**, each
    trimmed. They are ordered by event (setup, sessionstart, cwdchanged,
    filechanged), then by index as a number (2 before 10).
  - **Ignored:** empty files, other names (another event, another case, a
    suffix, a non-numeric index), and files that cannot be read.
  - **The parts are joined with `\n`.**
  - **On Windows** it is always `null`.
- **The result is cached for the process, `null` included.** New or changed
  files are not seen until `invalidateSessionEnvCache()`. Switching the
  session does not invalidate the cache either: after `/clear` or `/resume`,
  the previous session's script stays in force until something invalidates
  it (see Findings).
- **`clearCwdEnvFiles()`** truncates every `cwdchanged-hook-<n>.sh` and
  `filechanged-hook-<n>.sh` in the directory to empty. Every other file is left
  alone, and the cache is not invalidated.
- **`getSessionEnvVars()`** is an empty map, and `clearSessionEnvVars()` keeps
  it empty (see Findings).

`src/sessions/__fixtures__/rewrite/session-env/` pins the naming and the
assembly. `hook-files/` holds a directory as a session would, with names that
must be ignored among them. `parent-env.sh` is a `CLAUDIN_ENV_FILE`, and
`expected-script.sh` is the script they combine into, without its final
newline.

### 7. Session state and activity

**State.** It starts `idle`, and `getSessionState()` returns the last state
notified. Each `notifySessionStateChanged(state, details)` does the following,
in this order:
1. **The state listener** receives `(state, details)`.
2. **The pending action.** A `requires_action` with details publishes
   `{ pending_action: details }` to the metadata listener. Any later
   transition withdraws it once, with `{ pending_action: null }`. That
   includes a `requires_action` without details. A second `requires_action`
   with details replaces the first with no `null` in between.
3. **The mid-turn summary.** Every `idle` transition publishes
   `{ task_summary: null }` to the metadata listener, after the withdrawal.
4. **The SDK stream.** When `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS` is truthy
   (read at every transition), `{ type: 'system', subtype:
   'session_state_changed', state }` is queued with `enqueueSdkEvent`. The
   queue keeps it only in a non-interactive session, and hands it out with a
   `uuid` and the `session_id`.

**The listeners.** Each of the three listeners is a single slot: setting one
replaces the previous one, and `null` detaches it. Without listeners, the
notifications still update the state.

**The other notifications.** `notifySessionMetadataChanged(metadata)` hands
the object as-is to the metadata listener. `notifyPermissionModeChanged(mode)`
hands the mode to the permission-mode listener.

**Activity.** It is a count of work in flight, with a count per reason.
- **Stopping below zero** does nothing.
- **Tracking** is active exactly while a keep-alive callback is registered.
  Registering again replaces the callback.
- **The heartbeat.** While the count is above zero and a callback is
  registered, a heartbeat fires every 30 seconds from the first start.
  - Each beat logs `session_keepalive_heartbeat` at level `debug`, with
    `{ refcount }`, to the diagnostics log (`CLAUDIN_DIAGNOSTICS_FILE`).
  - It calls the callback only when `CLAUDE_CODE_REMOTE_SEND_KEEPALIVES` is
    truthy, read at each beat.
  - It stops when the count returns to zero or the callback is unregistered.
  - Registering a callback while work is in flight starts it; there is only
    ever one.
- **The idle note.** When the count returns to zero with a callback
  registered, `session_idle_30s` is logged at level `info` 30 seconds later,
  once. New work, or unregistering, cancels it.
- **`sendSessionActivitySignal()`** calls the callback at once, and only when
  keep-alives are switched on.
- **At shutdown.** The first start registers one shutdown cleanup per
  process. It logs `session_activity_at_shutdown` at level `info` with:
  - `refcount`;
  - `active`, the count per reason, leaving out the reasons at zero;
  - `oldest_activity_ms`: the time since the count last left zero, or `null`
    when nothing is in flight.

### 8. The process record: `<config dir>/sessions/<pid>.json`

`src/sessions/__fixtures__/rewrite/pid-record.registered.json` and
`pid-record.updated.json` pin the format, with the per-run values replaced by
placeholders.

**`registerSession()`:**
- **A teammate** (`getAgentId()` set) is not registered. It returns false and
  writes nothing.
- **Otherwise it writes the record:**
  - the directory is created owner-only (0700), and an existing one is
    `chmod`ed to 0700;
  - the record is written through `writePidRecord`: owner-only (0600) and
    atomic. Its fields are `{ pid, sessionId, cwd: getOriginalCwd(), startedAt:
    Date.now(), kind: 'interactive', entrypoint: CLAUDE_CODE_ENTRYPOINT }`, and
    the key is absent when the variable is unset.
- **It registers a shutdown cleanup** that deletes the record.
- **It follows session switches.** Every later `switchSession` or
  `regenerateSessionId` (`/resume`, `/clear`) patches `sessionId`. Calling it
  again keeps only the newest follower.
- **It returns true.** Any failure (for instance, the sessions path is a file)
  returns false and is logged at debug level. It never throws.

**`whenSessionRegistered()`** stays pending until the first registration
attempt of the process, and resolves with that attempt's outcome. A later
attempt does not change it.

**The update functions** merge their fields into this process's record
through `patchPidRecord`, and keep every other field. Updates issued together
all land, and the record stays owner-only.

| Function | Fields |
|---|---|
| `updateSessionName` | `name`. An empty or missing name writes nothing |
| `updateSessionBridgeId` | `bridgeSessionId`; `null` is written as `null` |
| `updateSessionInbox` | `messagingSocketPath`, `messagingToken`; `null`s withdraw them |
| `updateSessionCwd` | `cwd` |
| `updateSessionStatus` | `status` |
| `updateSessionPresence` | `turnActive`, `runningAgents`, `costUSD` |

Without a record on disk, an update resolves quietly and creates nothing.

**`countConcurrentSessions()`:**
- **The candidates** are the files named exactly `<digits>.json` in the
  sessions directory. Every other file is ignored and kept.
- **What counts:** this process's own record, and every record whose pid is
  running (`isProcessRunning`, a signal-0 probe). The content is never read.
- **Stale records.** The record of a pid that is not running is deleted,
  except on WSL, and without being awaited.
- **A missing or unreadable directory** gives 0.

**`listLiveSessions(deps)`.** The defaults are the config's sessions
directory, `process.pid` and `isProcessRunning`.
- **The candidates** are the same file names, apart from this process's own
  record and the records of pids that are not running.
- **Each record is parsed**, and needs `pid` (a whole number), `sessionId`
  and `cwd`.
- **Only `pid`, `sessionId`, `cwd`, `turnActive`, `runningAgents` and
  `costUSD` are returned.** The name, status, bridge id and inbox token are
  not.
- **What is skipped:** unreadable, non-JSON and non-matching records.
- **Nothing is ever deleted.** A missing directory gives `[]`.

### 9. Titles

**`extractConversationText(messages)`:**
- **What it takes:** the text of user and assistant messages, in order. That
  is string contents, and the `text` blocks of array contents.
- **What it leaves out:**
  - meta messages;
  - any message whose `origin` is set to something other than
    `{ kind: 'human' }`: task notifications, other agents, channels;
  - every other message type, and every non-text block.
- **The result** is the parts joined with `\n`, and only the last 1000
  characters when it is longer.

**`generateSessionTitle(description, signal)`:**
- **A blank description** (after trimming) gives `null`, and the model is not
  called.
- **Otherwise it makes one call to `queryHaiku`**
  (`src/providers/shims/claude.js`) with:
  - `userPrompt`: the trimmed description;
  - `systemPrompt`: one instruction text (below);
  - `outputFormat`: the JSON schema in
    `src/sessions/__fixtures__/rewrite/title-output-format.json`, an object
    with one required string field `title` and no other properties;
  - `signal`, passed through;
  - `options`: exactly `querySource: 'generate_session_title'` (a member of
    the `QuerySource` union in `src/agent/prompts/querySource.ts`),
    `agents: []`, `mcpTools: []`, `hasAppendSystemPrompt: false`, and
    `isNonInteractiveSession`, which is `getIsNonInteractiveSession()` at call
    time.
- **The reply:**
  - Its text blocks are joined without a separator and parsed as JSON.
  - A `title` string is trimmed, and an empty one gives `null`.
  - Extra fields are ignored.
  - Anything else gives `null`: not JSON, no `title`, a `title` that is not a
    string, an array.
- **A call that throws** (an unsupported structured output, a network error,
  an abort) is logged at debug level and gives the product name, `Claudin`
  (see Findings).

**The instructions** have to get the model to write a title that lets the user
recognize the session in a list. The facts they must state:
- the title is 3–7 words;
- it is in sentence case: only the first word and proper nouns capitalized;
- the answer is JSON with a single `title` field.

Good and bad examples (too vague, too long, wrong case) help, and the suite
does not pin them.

## Edge cases and errors

| Case | What the caller sees |
|---|---|
| A resume with no session id at all (no override, `result.sessionId` undefined) | No switch and no cost restore. The current session's own transcript path is adopted, and the resumed metadata is written into it, which creates a metadata-only file for the new session. Not pinned. Decision: fix (Findings) |
| A resume whose worktree was removed | The session stays where it is, and the worktree is recorded as exited (`worktree-state` with `null` at the end of the transcript) |
| `exitRestoredWorktree` when the original directory is gone | The process stays in the worktree directory, and the worktree session and the caches are still dropped |
| A plugin-hook load that rejects | The start goes on; the hooks still run |
| A plugin-hook load that rejects with a non-Error | The error log names the source that was starting and the value |
| Two hooks that both return `initialUserMessage` | The one that finished last wins. Not pinned |
| `CLAUDIN_ENV_FILE` missing, empty or a directory | Ignored; the hook files still load |
| A hook env file that is a directory | Skipped |
| The session env directory missing when clearing | Resolves; nothing is written |
| A record directory where a file should be | `registerSession` resolves false, and `countConcurrentSessions` gives 0 |
| A record named `<pid>.json` whose content says another pid | `listLiveSessions` judges liveness by the file name and returns the content's `pid`. Not pinned |
| A pid owned by another user | Treated as not running, so its record is swept by `countConcurrentSessions` (the sessions directory is per-user). Not pinned |
| The title call aborted through `signal` | The product name, like any failure |
| The title reply split over several text blocks | Joined, then parsed |
| `stopSessionActivity` without a start | Nothing; the count stays at zero |
| The shutdown log when nothing is in flight | `refcount: 0`, `active: {}`, `oldest_activity_ms: null` |

## Security requirements

**Pinned by the tests:**
- **The process record carries the peer inbox token.** It is written
  owner-only (0600), in a directory that is owner-only (0700). An existing
  directory with a looser mode is tightened.
- **`listLiveSessions` never returns the inbox token**, the name, the status or
  the bridge id. The resume picker and the session list get identity and
  presence only.
- **Updates to the record are serialized,** so concurrent updates never drop
  each other's fields. The record stays owner-only.
- **Plugin hooks are untrusted code.** They are not loaded when policy (or a
  non-managed `disableAllHooks`) allows only managed hooks, nor in bare mode.
- **A resumed fork never takes over the original session's worktree,** so the
  fork's exit dialog cannot remove a worktree the original still uses.

**Kept, but not pinned:**
- **Record writes are atomic** (write a sibling, then rename), so a reader
  never sees half a record. `writePidRecord` in `src/sessions/pidRecord.ts`
  provides this, and `pidRecord.test.ts` covers it.
- **The session environment script runs as shell code before every command.**
  Only this user's hooks and a parent-provided `CLAUDIN_ENV_FILE` may put text
  there. See the finding on the directory's mode.

## Findings

The old modules had each of these. None is fixed in the characterization: the
suite passes on the old code. What a "fix" would change is left unpinned.

1. **A failed title call gives `Claudin`, not `null`.**
   - Every thrown error does it, an abort included. The documented contract
     said `null`.
   - The REPL treats the product name as a real title: it shows it and saves
     it as the session's AI title. The SDK `generate_session_title` request
     answers with it, and persists it when asked to.
   - The fallback exists for providers without structured output.
   - **Decision: keep for parity.** The REPL retries after a `null` on every
     query, so returning `null` would call the model once per turn on such a
     provider, and the SDK answer would change. Track a failure result that
     callers can tell apart from "no title", and have them stop retrying on
     it.
2. **A plugin-hook load error loses its context in the error log.** For an
   `Error`, the logged text is the original stack, without the source that was
   starting. **Decision: fix.** It is logging only: log a message that carries
   both.
3. **The session environment script survives a session switch.** After
   `/clear`, `/resume` or `--resume`, commands keep sourcing the previous
   session's script until a cwd change or an outside-REPL hook invalidates it.
   The new session's own directory is ignored until then. **Decision: keep for
   parity.** A startup-only hook that activates a virtualenv relies on it: the
   new session's directory holds nothing from that hook, and a per-session
   cache would drop the environment at `/clear`.
4. **The session environment directory has the default mode** (0755 under
   the usual umask), and so does `session-env`.
   - The hook env files can hold exported secrets (tokens), and are readable by
     other local users when the home directory is traversable.
   - **Decision: fix, as pure hardening.** Create the directories owner-only
     (0700). The CLI and the hooks run as the same user, so legitimate use
     never notices.
5. **A resume without a session id writes a metadata-only transcript** for the
   new session (see Edge cases). **Decision: fix.** Adopt a transcript only
   when a session was taken over. The cached metadata is still written with
   the first message. Nothing can depend on an orphan file.
6. **Session env vars have no writer.** The `/env` command that would fill
   them does not exist, so the map is always empty. Both shell providers and
   `/clear` still call the two exports. **Decision: keep for parity** (the
   exports and their behaviour). Track either building the writer or removing
   the map together with its three callers.
7. **`whenSessionRegistered` keeps the first outcome.** A registration that is
   skipped (a teammate) and later succeeds still resolves false. **Decision:
   keep for parity.** Production registers once per process.
8. **The error log is empty at the default privacy level.** `logError` records
   nothing, even in memory, at Claudin's default privacy level, so a failed
   plugin-hook load is visible only in the debug and diagnostics logs. This is
   outside the unit (`src/shared/log.ts`, `src/platform/config/privacyLevel.ts`).
   Track.

## Target design

- **One slice, one directory.** The code goes under
  `src/sessions/lifecycle/`, one module per concern:
  - `restore/`: the resume orchestration, the agent, the state rebuilt from the
    transcript, and the worktree move;
  - `startHooks`;
  - `environment`;
  - `state`;
  - `activity`;
  - `title`;
  - `processRecord`.

  Until every caller is rewritten, the eight current paths stay as thin
  facades that re-export the contract.
- **The resume as a pipeline.**
  - **Parts.** A pure function turns the loaded result and the options into a
    plan: take over or fork, which id, which project directory. Small effects
    carry the plan out: switch, cost, metadata, worktree, adoption, agent,
    mode, process-record name.
  - **Order.** The order stays in one visible place, because the order is the
    behaviour: metadata before the worktree check, the worktree check before
    adoption.
  - **Coordinator mode** stays behind `feature('COORDINATOR_MODE')`, with its
    three effects together and the mode API passed in, as now.
- **Directory caches.** One function drops every cache keyed to the working
  directory. Both worktree moves use it, so a cache added later cannot be
  forgotten in one of them.
- **The start hooks.** One function serves both events and takes the event,
  the matcher query and the options. The additional-context attachment is
  built in one place. The initial user message keeps its take-once slot.
- **The environment.**
  - **Parts.** Naming and ordering are a pure function from file names to an
    ordered list. The script assembler takes a directory and the parent file.
  - **The cache** is an explicit, invalidatable value; decision 3 keeps it
    process-wide.
  - **Directories** are created owner-only (decision 4).
- **State and activity.**
  - **State.** A small typed state holder with three single-slot listeners.
    The metadata mirror (pending action, summary clear) is a pure function of
    the previous flag and the transition.
  - **Activity.** A counter with per-reason counts. The heartbeat and idle
    timers are scheduled through the globals at call time, as the tests
    require.
- **The title.** The prompt, the output schema and the reply parser are
  separate. The parser is pure: reply text in, title or `null` out. The model
  call stays `queryHaiku` from `src/providers/shims/claude.js`.
- **The process record.** The path, the record builder and the reader schema
  sit in one module. Writes go through `writePidRecord` and `patchPidRecord`.
  The liveness probe and the sessions directory are injectable, as in
  `listLiveSessions` today.
- **Types.** Explicit throughout, with no `any`. Named parameter types for
  the resume options and context stay structurally identical to today's.
  Errors go to `logForDebugging` or `logError`; none is swallowed silently.
